# DevChats — план разработки

Бесплатный, открытый (open-source) десктоп-мессенджер (аналог Discord),
который **не зависит от серверов сервиса**: каждый пользователь сам
поднимает свой узел (node), и соединение идёт напрямую по `IP:port`.

---

## 1. Концепция и архитектура

### Модель «каждый — сервер»

Каждый запущенный экземпляр DevChats — это **узел** (node): одновременно
клиент (UI) и сервер (принимает входящие подключения). Два вида узлов:

| | Локальный узел | Постоянный узел (фаза 2) |
|---|---|---|
| Где работает | Внутри десктоп-приложения | Отдельная программа на Linux |
| Когда доступен | Пока приложение запущено | 24/7 (systemd / Docker) |
| Возможности | Полный набор | Полный набор |
| Код | `server-core` (встраивается) | `server-core` (standalone-обёртка) |

Ключевое решение: **вся серверная логика — в общей библиотеке `server-core`**.
Десктоп-приложение встраивает её в себя; будущий постоянный сервер — просто
отдельная точка входа поверх той же библиотеки. Один и тот же код, один протокол.

### Как происходит общение

- Пользователь А знает адрес пользователя Б: `IP:port`.
- А подключается к узлу Б (WebSocket). Б **должен быть в сети** — его локальный
  узел запущен (либо у Б есть постоянный сервер на Linux).
- Если Б офлайн: сообщение не доставляется сразу. Узел А кладёт его в **исходящую
  очередь**; при следующем подключении Б к А (или наоборот) происходит
  **синхронизация почтового ящика** (mailbox sync) и сообщения доставляются.
- Дополнительно: узел может вести **каналы** (text/voice) — тогда участники
  подключаются к нему, как к «серверу» в Discord. Когда владелец узла офлайн,
  его каналы недоступны (по задумке).

### Стек

- **Язык/UI:** Kotlin, Compose Multiplatform (desktop: Windows / macOS / Linux)
- **Сеть:** Ktor (клиент + сервер), WebSocket, JSON через kotlinx.serialization
- **Хранилище:** SQLite (через Exposed или SQLDelight)
- **Асинхронность:** Coroutines / Flow
- **Сборка:** Gradle (уже есть wrapper 9.4, JDK 25)
- **Голос/видео (фаза 5–6):** WebRTC — точное решение принять на этапе M5
  (см. «Открытые вопросы»)

## 2. Структура проекта (Gradle multi-module)

```
DevChats/
├── settings.gradle.kts / build.gradle.kts
├── protocol/        — общие DTO, схемы сообщений, версия протокола
│                      (kotlinx.serialization) — используется всеми модулями
├── server-core/     — логика узла: Ktor-сервер (WebSocket + HTTP API),
│                      SQLite (почтовый ящик, каналы, файлы), маршрутизация
├── client-core/     — менеджер подключений: Ktor-клиент, состояние
│                      соединений, очередь исходящих, синхронизация почты
├── desktop/         — Compose UI (зависит от client-core + server-core)
└── server-standalone/ — (фаза 2) точка входа постоянного сервера на Linux
```

Модули `protocol` и `server-core` — общие для десктопа и постоянного сервера.

## 3. Протокол (WebSocket + JSON, версионируемый)

Каждое сообщение — JSON-объект-конверт:

```json
{ "v": 1, "type": "dm.send", "id": "uuid", "payload": { ... } }
```

Основные типы сообщений:

| Тип | Назначение |
|---|---|
| `hello` / `hello.ack` | Рукопожатие: nodeId, displayName, версия протокола |
| `auth.request` / `auth.accept` / `auth.deny` | Верификация подключения (доверие по адресу, блокировки) |
| `presence` | Статус онлайн/офлайн/занят и подписка на присутствие |
| `dm.send` / `dm.recv` | Личные сообщения (с доставкой через почтовый ящик) |
| `mailbox.sync` / `mailbox.items` | Синхронизация недоставленных сообщений |
| `channel.list` / `join` / `leave` | Каналы узла |
| `msg.send` / `msg.recv` / `msg.history` | Сообщения в каналах, история |
| `file.offer` / `file.chunk` / `file.done` / `file.abort` | Передача файлов чанками + контрольная сумма |
| `call.invite` / `call.answer` / `call.ice` / `call.end` | Сигналинг WebRTC для голоса/видео |
| `ping` / `pong` / `bye` | Поддержание и закрытие соединения |

Правила:
- Версия протокола проверяется на `hello`; при несовпадении — понятная ошибка.
- Каждое сообщение имеет `id`; приёмник отвечает `ack`, отправитель пересылает
  недополученное при повторном подключении.

## 4. Хранилище (SQLite)

**На стороне узла (server-core):**
- `mailbox` — недоставленные личные сообщения (inbox/outbox)
- `channels`, `channel_messages`, `members`
- `files` — индекс файлов каналов и DMs
- `peers` — список известных узлов (nodeId → имя, адрес, блокировки)

**На стороне клиента (desktop):**
- `contacts` — сохранённые адреса `IP:port`
- `servers` — подключённые узлы/каналы
- `message_cache` — кэш истории для офлайн-просмотра
- `settings` — имя, порт, тема, аватар

## 5. Функциональность (что уже согласовано)

Всё «как в Discord», но на своей инфраструктуре:

- Текстовые каналы и серверы (узлы), DM
- Голосовые каналы и звонки
- Видео и демонстрация экрана
- Передача файлов (drag & drop, прогресс, докачка)
- Боты и API узла (HTTP + события по WebSocket, токен-авторизация)
- Присутствие (онлайн/офлайн), история сообщений

## 6. Дорожная карта (милистоуны)

### M0 — Каркас проекта
- KMP multi-module: `protocol`, `server-core`, `client-core`, `desktop`
- Окно Compose «DevChats» с заготовкой UI (список серверов / каналов / чат)
- Сборка зелёная: `./gradlew build`
- CI (GitHub Actions): сборка + тесты на Windows/Linux/macOS

### M1 — Ядро узла
- Встроенный Ktor-сервер поднимается при запуске приложения
- Настройки: имя, порт (по умолчанию фиксированный), аватар
- SQLite: схема БД, миграции
- `GET /health` — проверка, что узел жив
- Тесты: юнит-тесты сервера (Ktor test host)

### M2 — Подключение и присутствие
- Подключение по `IP:port` (кнопка «Добавить контакт»)
- Рукопожатие `hello`, проверка версии протокола
- Список контактов с индикатором онлайн/офлайн
- Авторизация: accept/deny на стороне узла, чёрный список

### M3 — Текстовые сообщения
- DM между узлами
- Создание каналов на своём узле, приглашение участников
- История сообщений, подгрузка при входе
- **Почтовый ящик**: офлайн-доставка + синхронизация при подключении
- Уведомления о новых сообщениях

### M4 — Передача файлов
- Drag & drop в чат
- Передача чанками (1 МБ), прогресс-бар, отмена
- Контрольная сумма (SHA-256), проверка целостности
- Докачка прерванной передачи; общий доступ к файлам каналов

### M5 — Голос
- Решение по WebRTC-стеку для JVM (см. «Открытые вопросы»)
- Сигналинг по WebSocket (`call.*`)
- Звонок 1-на-1 и голосовые каналы; индикатор говорящего

### M6 — Видео и демонстрация экрана
- Видеозвонки, переключение камер, мутинг
- Демонстрация экрана / окна / области

### M7 — Боты и API
- HTTP API узла (`/api/v1/...`) + события по WebSocket
- Токен-авторизация для ботов
- Пример бота (на Kotlin или другом языке) в репозитории

### M8 — Постоянный сервер на Linux
- Модуль `server-standalone` поверх `server-core`
- Упаковка: JAR + Docker-образ + systemd-юнит
- Инструкция «как задеплоить свой сервер»
- Десктоп подключается к нему как к обычному узлу по `IP:port`

### M9 — Хардненинг (после основного функционала)
- TLS (самоподписанные сертификаты + pinning), шифрование почтового ящика
- Надёжность: реконнекты, экспоненциальный backoff, обработка конфликтов
- Полный набор тестов: unit + integration (два узла в одном тесте)

## 7. Открытые вопросы

1. **WebRTC на JVM.** Голос/видео — самая рискованная часть. Варианты:
   - JNI-обвязка libwebrtc (например, `webrtc-java`) — полный WebRTC,
     но сложная сборка нативные библиотеки;
   - Jitsi Meet (`libjitsi`) — проверенный стек, тяжеловесный;
   - упрощённо: Opus + UDP напрямую (LAN), без NAT-обхода.
   Решение принимать на M5, но лучше заложить абстракцию «медиа-транспорт»
   уже сейчас, чтобы не переписывать сигналинг.
2. **NAT и обход.** По задумке пользователь «должен быть в сети» — то есть
   прямые подключения по `IP:port` без NAT-проброса. STUN/TURN/UPnP — отдельная
   тема на потом (или вообще вне scope).
3. **Точный порт по умолчанию** и его смена при конфликте.
4. **Имя/идентичность:** nodeId = UUID при первом запуске; псевдонимы и
   «дружеские адреса» (например, `name#tag`) решить на M2–M3.
5. **Шифрование** в MVP не планируется (LAN / доверенная сеть), но протокол
   проектировать так, чтобы TLS добавлялся без ломки совместимости.
